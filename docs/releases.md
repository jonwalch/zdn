# Optional signed package catalogs

For installing the unsigned public preview, use the
[release download and setup guide](preview-start.md). Its separate executable,
node-source/map and chain downloads do not require a signed catalog, a publisher
key, or any `release sign` command. Checksums detect byte changes; they are not
publisher signatures.

This page is an advanced reference for consumers of an explicitly trusted signed
catalog and for publishers creating one. It is not the preview installation
procedure, and it does not claim that public preview files are signed.

`zdn::releases` authenticates a bounded release catalog and selects an exact,
SHA-256-pinned deployment package. It does not introduce a new deployment format:
resolution uses the existing `package::Package` and `artifact_set::ArtifactSet`
verifiers. No artifact is executed by catalog verification, resolution, or export.

## Consumer workflow

Obtain a catalog, its detached signature, and a public key through separately
trusted channels. Consumers need no private signing key:

```sh
zdn release verify --catalog catalog.json --signature catalog.sig --trusted-key publisher.pub
zdn release resolve --catalog catalog.json --signature catalog.sig \
  --trusted-key publisher.pub --release v0.2.0-rc.1 --output selected
```

## Publisher workflow

Export an existing verified package, then sign a catalog that pins that export:

```sh
zdn package export --manifest package.json --sha256 "$PACKAGE_SHA256" --output exported
zdn release sign --catalog catalog.json --key publisher.pk8 --output catalog.sig
```

Prepare `catalog.json` with the schema below and the exported package's returned
raw `packageSha256`. There is no implicit catalog URL or default trust store.
The signing key is an existing unencrypted binary PKCS#8 Ed25519 file, either
v1 (as generated by OpenSSL) or v2. For v1 the public key is derived from the
private seed; v2 also checks the embedded public key for consistency. Key
generation and secure storage remain the publisher's responsibility. Verification
requires a separately trusted raw 32-byte public-key file. Repeat `--trusted-key` for explicit
rotation; no key is imported from the catalog. These commands bound catalog, key,
and signature reads and reject final symlinks/non-regular files.

`release verify` authenticates declarations without fetching or resolving any
package. `release sign` validates declarations, not package availability or safety.
`release resolve` verifies the exact selected package and exports it to a new,
durable data-only directory; it never installs, launches or publishes externally.
Relative package paths use the catalog file's containing directory, not the
current working directory. The report includes catalog digest, signer, release,
absolute exported manifest path, package pin and artifact-set fingerprint.

Feed the exported manifest and pin into existing `devnet render`/`devnet up`
`--package` and `--package-sha256` flags. The configuration must pin the package's
exact node image; all existing topology, chain, helper, ECR and authorization
checks remain unchanged. Plain package verification/export still reports
`publisherAuthenticated: false`: the detached catalog does not become a signature
on every later copy of the manifest. Retain the catalog digest/signer report if
you need that audit link. No report marks the release qualified or launch-ready.

Both machine formats work for these commands and `package export`. JSON has one
terminal result; JSONL has command-started followed by the terminal result. Errors
use fixed `release-verification-failed`, `release-resolution-failed`,
`release-signing-failed`, or `package-export-failed`, with blocked retry
classification and no raw paths/key material. `--progress-file` is rejected.
Signature files are published privately without replacement; package outputs use
the Linux/macOS atomic export described below. Existing destinations are never
replaced.
A final sync or output-stream failure can occur after publication: inspect the
destination before retrying, never assume failure means no file exists.

## Catalog and signatures

```json
{
  "apiVersion": "zdn-release-catalog/v1alpha1",
  "releases": {
    "v0.2.0-rc.1": {
      "location": { "kind": "file", "path": "v0.2.0-rc.1/package.json" },
      "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    }
  }
}
```

The example pin is illustrative, not a published release. Catalogs are nonempty
and limited to 2 MiB of raw JSON (`MAX_CATALOG_BYTES`). Unknown fields, unsupported
API versions, duplicate release keys (including escaped equivalent spellings),
invalid pins, and unsafe locations are rejected. Pins are 64 lowercase hex digits
over the exact package manifest bytes, not a reserialized JSON representation.

Identifiers use the shared configuration exact-release policy: 1–128 ASCII
letters/digits or `.`, `-`, `_`, excluding `latest`, `main`, `master`, `stable`,
and `nightly`. Candidate/prerelease identifiers are allowed, without implying
qualification. Lookup is exact and case-sensitive; there are no version ranges,
automatic updates, channel lookups, or fallback selection.

A detached signature is exactly 64 **raw binary bytes**, Ed25519 over the entire
raw catalog. Even a whitespace-only catalog edit requires a new signature.
Public keys are explicitly supplied, raw 32-byte Ed25519 keys; the catalog has no
key-discovery, key-import, or trust-on-first-use mechanism. Signatures are checked
before JSON decoding or package access.

The public preparation/authentication APIs are:

```rust,ignore
Catalog::from_json(bytes: &[u8]) -> eyre::Result<Catalog>
Catalog::validate(&self) -> eyre::Result<()>
releases::sign(bytes: &[u8], key: &ring::signature::Ed25519KeyPair)
    -> eyre::Result<[u8; 64]>
releases::verify(bytes: &[u8], signature: &[u8], trusted_keys: &[[u8; 32]])
    -> eyre::Result<VerifiedCatalog>
```

`Catalog` has `api_version: String` and
`releases: BTreeMap<String, PinnedPackage>`; `PinnedPackage` has
`location: package::Location` and `sha256: String`. Parsing or constructing a
`Catalog` alone establishes no trust and provides no release resolver. Signing
validates syntax and declarations but does not resolve/qualify every package.
The caller owns signing-key creation, secure storage, and separate trusted-key
distribution; `ring` 0.17.14 is reused from the existing lockfile.

`VerifiedCatalog` is immutable and exposes `catalog() -> &Catalog`,
`sha256() -> &str` (raw catalog digest), and `signer() -> &[u8; 32]` for audit.
Its `resolve(release: &str, base: &Path, overrides: &BTreeMap<String, PathBuf>)`
returns `eyre::Result<package::ResolvedPackage>`. The
`resolve_with_downloader` variant adds `downloader: &impl dependencies::Downloader`
for offline fixtures. Both accept relative file package locations. Remote package
locations must use HTTPS, even when transport is injected; this is not a
requirement to fetch the catalog itself over HTTPS. The CLI reads the catalog
from the local `--catalog` file. Production package downloads use the bounded
`HttpDownloader`.

File package locations are relative to the explicitly supplied catalog directory
(`base`); artifact file sources remain relative to that package manifest's parent.
The package module owns path, symlink, URL, size, hash, inventory, and semantic
validation. HTTPS package manifests are bounded independently of their downloader
and checked against their raw pin before any artifact fetch. HTTPS manifests must
use HTTPS artifact sources or explicit pinned local overrides: file sources are
not rebased onto remote URLs or a user's checkout. Overrides cannot change hashes,
inventory, compatibility, or provenance. Temporary resolved storage is deleted
when the `ResolvedPackage` is dropped.

## Self-contained local preparation (Linux and macOS)

```rust,ignore
package::export(directory: &Path, artifact_set: &ArtifactSet, destination: &Path)
    -> eyre::Result<package::ExportedPackage>
```

The existing destination parent must be caller-owned. Export verifies the source
artifact set before staging and verifies the copied snapshot again. It writes
only `package.json` and the fixed artifact inventory, with private directory mode
0700 and file modes 0600 (including the inert helper bytes). It does not export
extra checkout files, symlinks, executable permissions, hooks, or scripts.

The new manifest replaces source locations with flat relative file locations.
The artifact set, raw artifact pins, image identity, and original provenance are
unchanged; no build or release provenance is invented. The return value contains
`manifest: PathBuf` and `sha256: String`, the new raw package pin to put in a
catalog. The exported directory can be moved and the original checkout and
temporary resolved storage deleted before resolution.

Publication to the local destination is one `renameat2(RENAME_NOREPLACE)` on
Linux or `renameatx_np(RENAME_EXCL)` on macOS, after file and staging-directory
synchronization. Existing files, empty/nonempty directories, and symlinks cannot
be replaced. Errors before rename clean up the
staging directory. Unsupported filesystems fail rather than fall back to an
overwrite-prone rename; this API is compiled only on Linux and macOS. The parent
directory is synchronized after rename; if that final sync fails, a complete export may
already exist and callers must inspect it rather than assume nothing was written.
Atomic visibility and crash durability remain subject to filesystem guarantees.
Mac support is for client-side data preparation only: packaged node images and
host helpers must still satisfy the existing Linux runtime contracts.

## Trust and deferred acceptance

Authentication proves only that a supplied trusted key signed these declarations.
It does not prove reproducibility, source authenticity, licensing, image registry
availability, chain correctness, wallet/lightwalletd compatibility or qualification,
or that executing any packaged helper/image is safe. Embedded provenance remains
a declaration checked for consistency, not independently attested history.

This stateless library cannot prevent a trusted publisher from signing a newer
catalog that rebinds an identifier, or detect replay/rollback of an older signed
catalog. Callers must retain accepted catalog digests/release bindings and manage
revocation/freshness outside this slice if required. A public key fetched together
with an untrusted catalog is not a trust anchor.
